# API-тесты Stellar Burgers

Учебный проект на Java 11, Maven, JUnit 5, RestAssured, AssertJ и Allure.
Адрес API: `https://qa-stellarburgers.education-services.ru`.

## Что находится в проекте

Весь Java-код расположен в `src/test/java/stellarburgers`:

- `tests/CreateUserTest` — уникальная и повторная регистрация, отсутствие каждого обязательного поля (5 проверок).
- `tests/LoginUserTest` — успешный вход, неверный email и неверный пароль по отдельности (3 проверки).
- `tests/UpdateUserTest` — изменение email, name и password с авторизацией и без неё (6 проверок).
- `tests/CreateOrderTest` — четыре указанных сценария создания заказа (4 проверки).
- `tests/GetUserOrdersTest` — получение своих заказов и отказ без авторизации (2 проверки).
- `tests/BaseApiTest` — подготовка пользователя и удаление через `@AfterEach`, в том числе после падения проверки.
- `client` — повторяющиеся запросы пользователей, заказов и ингредиентов; `ApiRequest` задаёт адрес и таймауты.
- `model/UserData` — email, password и name для запросов. Поля со значением `null` не отправляются в JSON.
- `support/ApiAssertions` — общие проверки статуса и тела ответа с русскими Allure-шагами.

Всего 20 запусков тестов с учётом параметризации. Данные каждого пользователя уникальны.
Токен для удаления сохраняется сразу после регистрации, до проверок ответа.
Идентификаторы ингредиентов запрашиваются у API, а не берутся из PDF.
Сохранение email и имени проверяется через GET профиля, пароля — через вход с новым паролем.
Для получения заказов сначала создаётся заказ, затем проверяются его номер и ингредиенты в ответе.

Пароли и токены не логируются. HTTP-запросы и ответы целиком не прикладываются к Allure.
У `UserData` намеренно нет `toString()`, раскрывающего поля: Allure записывает аргументы `@Step`.

## Запуск на Java 11

Для macOS:

```bash
cd /Users/kaspi/Desktop/Project/Task_2
export JAVA_HOME=$(/usr/libexec/java_home -v 11)
export PATH="$JAVA_HOME/bin:$PATH"
mvn -version
mvn clean test
```

В выводе `mvn -version` должна быть строка `Java version: 11...`.
Maven Enforcer останавливает сборку, если Maven запущен на другой версии Java.
JUnit BOM согласует версии JUnit Jupiter и JUnit Platform, включая зависимости Allure.

## Allure HTML-отчёт

После запуска тестов выполните отдельно, даже если тесты упали:

```bash
mvn allure:report
open reports/allure-report/index.html
```

Генерация отчёта не запускает тесты повторно. Не выполняйте `mvn clean` между тестами и генерацией:
это удалит исходные результаты из `target/allure-results`.

`reports/allure-report/index.html` — автономный HTML-файл: его можно открыть без сервера
или передать проверяющему. В нём доступны результаты, параметры сценариев и шаги подготовки,
действий, проверок и очистки. Файл находится вне `target` и может войти в pull request.
После нового запуска сформируйте отчёт заново: предыдущий HTML сам не обновляется.

## Неоднозначности документации

Ожидания взяты из предоставленного `api-Stelar_Burger_10.25.pdf`, домен заменён по условию задания.

- На стр. 5 сказано, что только авторизованные пользователи могут создавать заказы.
  При этом стр. 1 не описывает отказ для POST `/api/orders` без токена. Тест проверяет запрет;
  HTTP 401 и наличие сообщения — явно принятое предположение по аналогии с другими защищёнными ручками.
  Точный текст ошибки здесь не выдумывается. Возврат успешного заказа будет считаться расхождением
  с требованием стр. 5, а не причиной ослаблять тест.
- Для неверного хеша ингредиента на стр. 1 указан HTTP 500, но нет схемы и текста тела ошибки.
  Проверяются этот статус и непустое тело. Это минимальная проверка тела, а не подтверждение его схемы.
- Успешные HTTP-статусы в PDF не перечислены. Для основных успешных операций используется HTTP 200;
  для вспомогательного DELETE пользователя — HTTP 202 и `success: true`. Эти статусы требуют
  уточнения контракта, даже если подтверждаются запуском сервера.
- Операция удаления заказа не описана. Тесты удаляют созданных пользователей, но не вызывают
  выдуманный DELETE заказа; сохранность заказов после удаления пользователя сервером не гарантируется.

Фактический результат запуска и расхождения приведены в [отчёте для PR](reports/README.md).

## Отправка ветки develop2

```bash
git branch --show-current
git status --short
git diff --check
git add .gitignore pom.xml README.md src/test/java reports
git diff --cached --stat
git commit -m "Add Stellar Burgers API tests and Allure report"
git push -u origin develop2
```

Перед коммитом убедитесь, что текущая ветка — `develop2`. Папка `target` уже исключена через `.gitignore`.
В pull request включите итог запуска и известное расхождение, описанные в `reports/README.md`.
